## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Luồng sinh `test_set.json` (đánh giá AI). Khi chạy lần đầu, cờ `refresh_test_set` mặc định là False, khiến code bỏ qua việc gọi hàm sinh câu hỏi, gây lỗi `FileNotFoundError` ở bước Evaluation sau đó.
- **Các phương án đã cân nhắc:**
  1. Yêu cầu mọi người trong nhóm phải chủ động set biến môi trường `REFRESH_TEST_SET=1` trong file `.env` khi chạy lần đầu.
  2. Bổ sung logic kiểm tra sự tồn tại của file ngay trong luồng Orchestration: `if settings.refresh_test_set or not settings.paths.eval_testset.exists():`
- **Phương án đã chọn:** Phương án 2 (Tự động kiểm tra sự tồn tại của file).
- **Lý do:** Trade-off mang tính UX và Automation. Tôi không muốn nhóm phải tốn công nhớ cấu hình biến môi trường thủ công. Code phải thông minh tự hiểu là chưa có file thì phải sinh file. Điều này tăng tính reproducibility.
- **Bằng chứng quyết định phù hợp:** Chạy lệnh terminal ngay sau khi xoá file `test_set.json` vẫn không bị crash hệ thống.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:**
  ```text
  File "src/ingestion/cleaning.py", line 34, in build_clean_dataframe
      raise ValueError("run_date must be a valid datetime")
  ValueError: run_date must be a valid datetime
  ```
- **Lệnh hoặc bước tái hiện:** `python script/run_phase1.py`
- **Nguyên nhân gốc:** Ở hàm `main()` của `phase1.py`, tôi đã truyền cứng giá trị `run_date=None` vào hàm `build_clean_dataframe`. Điều này làm module Cleaning ném lỗi vì nó cần 1 mốc thời gian (datetime) hợp lệ để tính khoảng cách ngày (`age_days`) phục vụ cho bước đánh giá Freshness.
- **Cách xử lý:** Import thư viện `from datetime import UTC, datetime` và thay đổi tham số truyền vào thành `run_date=datetime.now(UTC)`.
- **Cách xác minh sau khi sửa:** Chạy lại `python script/run_phase1.py`, code vượt qua bước clean và lưu `papers_clean.csv` thành công.
- **Điều học được:** Khi làm nhiệm vụ tích hợp/orchestration, phải tuân thủ nghiêm ngặt data type và signature (chữ ký hàm) của các thành viên khác quy định.

## 7. Hiểu biết về luồng end-to-end

1. **Dữ liệu đi từ Crossref đến vector index như thế nào?**
   Dữ liệu thô tải từ API dưới dạng JSON -> Truyền qua module Clean lọc bỏ bài viết lỗi/null, chuẩn hoá Datetime -> Chuỗi hóa (nối Title, Authors, Summary) thành chuỗi `text_for_embedding` -> Đưa qua model SentenceTransformers mã hoá thành các dãy vector -> Nhét vào ChromaDB lưu tại ổ cứng.
2. **Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?**
   Ground-truth document ID đóng vai trò làm cờ "đánh dấu" tài liệu đúng. Khi user (Agent) truy vấn, ChromaDB trả về các tài liệu gần nhất. Ta kiểm tra xem ID trả về có trùng với ground-truth ID không (để tính `retrieval_hit_rate`). Nếu tìm đúng, Agent sẽ đọc tài liệu để sinh câu trả lời, giám khảo sẽ đối chiếu câu trả lời này với chuỗi Ground truth văn bản để tính Accuracy.
3. **Quality checks khác freshness monitoring ở điểm nào trong bài lab?**
   Quality checks là công việc kiểm định cấu trúc tĩnh (null, độ dài chuỗi, uniqueness) để bảo đảm schema dữ liệu. Còn Freshness theo dõi SLA về mặt thời gian (dữ liệu có bị "ôi thiu" hay cũ quá hạn 180 ngày so với thời điểm chạy không).
4. **Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?**
   Để duy trì tính công bằng (Biến số kiểm soát - Control variable). Nếu đổi câu hỏi khác, ta không thể biết được sự sụt giảm điểm số là do Data bị rác hay là do câu hỏi mới khó hơn.
5. **Repair được xem là thành công dựa trên artifact và metric nào?**
   Thành công khi Quality Gate báo xanh lại (Success = 1.0) và các chỉ số Agent (hit_rate, mean_token_f1, mean_judge_score) phục hồi y hệt mức ban đầu của Baseline.

## 8. Phân tích kết quả

### Metrics chính

| Metric/signal          | Baseline | Corrupted | Repaired | Nhận xét của cá nhân |
| ---------------------- | -------: | --------: | -------: | ------------------------- |
| `retrieval_hit_rate` |     1.0 |      0.5 |     1.0 | Khi data hỏng, mất ID/summary, khả năng search của ChromaDB giảm một nửa. |
| `mean_token_f1`      |     0.4869 |    0.2165 |    0.4869 | Trùng khớp từ vựng sụt giảm mạnh do LLM trả lời "ảo giác" hoặc "tôi không biết". |
| `judge_accuracy`     |     0.5 |    0.2 |     0.5 | Từ 50% câu trả lời đúng xuống còn 20%. Rất tệ. |
| `mean_judge_score`   |     2.8 |     1.8 |     2.8 | Điểm trung bình bốc hơi 1 điểm. |
| Quality checks         |   Pass |      Fail (0.0)|    Pass (1.0) | Hệ thống bắt được sự cố dữ liệu, còi báo động Quality Gate hoạt động tốt. |
| Freshness status       |   Pass |      Pass |      Pass | không cố tình sửa đổi cột published làm cũ bài báo nên Freshness giữ nguyên. |

### Kết luận từ số liệu

1. **[Data corruption] → [quality/freshness signal thay đổi] → [agent metric thay đổi].**
   Khi chọc ngoáy dữ liệu làm mất đi trường ID và cắt cụt Summary, hệ thống Quality Gate Great Expectations báo `success = 0.0` ngay lập tức. Agent RAG không còn ngữ cảnh văn bản để tìm -> `hit_rate` sụt giảm 50%, `judge_score` tụt còn 1.8.
2. **[Repair action] → [quality/freshness signal phục hồi] → [agent metric phục hồi hoặc chưa phục hồi].**
   Bằng cách loại bỏ bảng Corrupted và nạp lại từ File Snapshot JSON bất biến ban đầu (Idempotent), hệ thống lấy lại nguyên vẹn text. Qua đó, hàm Quality check pass 1.0 trở lại, phục hồi 100% sức mạnh RAG (1.0 hit_rate và 2.8 score).

Corruption ảnh hưởng rõ nhất là việc **làm mất/rỗng Summary và Title**, vì hai trường này là nguồn sống chính yếu tạo nên Vector Embedding. Khi nó thành rỗng, ChromaDB mất phương hướng hoàn toàn.

Kết quả nào khác với kỳ vọng ban đầu?
Điểm `mean_judge_score` của Baseline chỉ đạt 2.8/5.0 thay vì 4 hoặc 5 như tôi mong đợi. Giả thuyết là LLM Giám khảo rất khắt khe, Ground Truth là một câu cực ngắn (như 1 chuỗi Tên Tác Giả), trong khi LLM RAG trả lời thành một câu hoàn chỉnh dài dòng, dẫn đến F1 bị thấp và Giám khảo trừ điểm.

## 9. Điều học được và hướng cải thiện

### Ba điều quan trọng nhất

1. **Orchestration Rất Dễ Gãy:** Khi ráp nối 4 đoạn code của 4 lập trình viên khác nhau, việc không nắm rõ Contract/Chữ ký hàm (Signatures) sẽ khiến hệ thống sập ngay từ lần chạy đầu tiên.
2. **Quality Gate là Khiên Chắn Sống Còn:** Đừng nạp thẳng data thô vào VectorDB. Nếu không có bước Quality Gate (Great Expectations) bắt lỗi Null, chúng ta sẽ lãng phí tiền API LLM cho những prompt rác.
3. **Data Lineage và Snapshot:** Trong Data Engineering, luôn phải giữ lại file Raw JSON không đụng tới. Khi có sự cố (Corruption), ta không thể "Ctrl+Z" trên file CSV đã hỏng, mà phải reload từ bản Snapshot nguyên thuỷ.

### Nếu có thêm thời gian

Tôi sẽ cải tiến Prompts của Giám khảo LLM và RAG Agent. Đưa thêm kịch bản Few-shot prompting hoặc đánh giá ngữ nghĩa (Semantic similarity) thay vì dựa quá nhiều vào Exact match / Token F1, để đo lường mức cải thiện `mean_judge_score` lên mức > 4.0.
